# HHOF Goalie Sim — Goal Detector

Camera-based goal detection for the Hockey Hall of Fame goalie simulator.
Single-process-per-net architecture. Connects to a Node WebSocket server to
emit goal events and receive shot-incoming notifications.

---

## Files in this project

```
goal_detector.py     - the detector (Python)
```

## Quick start

### Install deps (one time)

```bash
# Python deps
pip3 install opencv-python numpy websockets --break-system-packages
#   (use --break-system-packages on Debian/RPi OS Bookworm+)

# Node deps for the dev broker
npm install
```

### Run

Three things happen in parallel:

```bash
# Terminal 1: WebSocket broker + dashboard
node server.js
#   -> WS at ws://localhost:8765
#   -> dashboard at http://localhost:8080

# Terminal 2: calibrate (first time only, or whenever camera moves)
python3 goal_detector.py --calibrate

# Terminal 2 (again): run detector
python3 goal_detector.py            # production / headless
python3 goal_detector.py --debug    # with overlay windows
```

### Common command-line overrides

```bash
python3 goal_detector.py --source 1                     # specific webcam index
python3 goal_detector.py --server ws://hostname:8765    # specific server URL
python3 goal_detector.py --net-id net_2                 # override net identifier
python3 goal_detector.py --debug                        # show overlay windows
```

## Calibration

`--calibrate` opens an interactive 4-step GUI. It needs a display attached
(directly, via VNC, or via SSH X-forwarding).

1. **Capture frame** — point camera, press `SPACE`. Press `Q` to abort.
2. **Goal line** — click LEFT POST, then RIGHT POST on the goal line (where
   it meets the ice). Press `ENTER` to accept, `R` to reset.
3. **Net interior** — click 4+ vertices outlining the inside of the net
   (where pucks count as IN). Press `ENTER` to accept, `R` to reset.
4. **Approach zone** — click 4+ vertices outlining the area **in front of**
   the goal (the shooting / approach zone). The net ROI and goal line stay
   visible for reference. Drawn in cyan. Press `ENTER` to accept, `R` to reset.

All four regions are saved to `config.json`. The approach zone is needed so
pucks are detected before they cross the line — without it the tracker has
no "before" position to compare against and goals are missed. If you run
without a saved `approach_roi` (e.g. an old config), the script falls back
to auto-computing it by mirroring the net polygon across the goal line, and
logs a reminder to re-run `--calibrate`.

Re-run `--calibrate` any time:
- The camera moves
- Lighting changes substantially
- You change the camera mount

## Operating modes

The detector has two modes for when to look for goals:

- **Armed (default):** only counts a goal during a 1-second window after
  receiving a `shot_incoming` message. Emits `no_goal` if the window
  expires without a goal. Designed for integration with the Node app's
  game logic.
- **Always on:** counts any line-crossing into the net at any time. Useful
  for testing, demos, or installations where there's no shot-trigger
  signal.

Toggle from the receiver dashboard, or send `{"type": "set_mode", "mode": "always_on"}`
(or `"armed"`) over WebSocket. Set `always_on_default` in config to choose
the boot mode.

## Configuration reference

All settings live in `config.json` (created by `--calibrate`). Defaults
shown in `[brackets]`. Every field is optional in the file — missing keys
fall back to defaults.

### Identity & connection

| Key | Default | Description |
|---|---|---|
| `net_id` | `"net_1"` | Identifier for this net. Sent in every WebSocket message; the Node app uses this to route shot/goal events between multiple sims. Override per-Pi (`net_1`, `net_2`, etc). |
| `server_url` | `"ws://localhost:8765"` | WebSocket server to connect to. The dev `server.js` runs on this port; for production point at the real Node app. |

### Camera

| Key | Default | Description |
|---|---|---|
| `source` | `0` | Camera index (`0`, `1`, …) or path to a video file for offline replay. |
| `frame_width` | `1280` | Capture resolution. The OV9281 native is 1280×800 mono. |
| `frame_height` | `720` | |
| `target_fps` | `120` | Requested framerate. Camera/driver may negotiate lower; check the startup log to see what was actually negotiated. |
| `capture_backend` | `"auto"` | OpenCV capture backend. `"auto"` picks DSHOW on Windows, V4L2 on Linux, ANY elsewhere. Force one of `"dshow"` / `"msmf"` / `"v4l2"` / `"any"` if auto picks wrong. |
| `auto_exposure` | `true` | Let the camera/driver control exposure. Set `false` to force `manual_exposure` (useful when auto-exposure is silently capping framerate by using long exposures in dim light). |
| `manual_exposure` | `-7` | log2(seconds). `-7` ≈ 1/128s. Only applied when `auto_exposure` is false. |

### Calibration data (set by `--calibrate`)

| Key | Default | Description |
|---|---|---|
| `goal_line` | `null` | `[[x1,y1],[x2,y2]]` — two endpoints of the goal line in image coordinates. |
| `net_roi` | `null` | `[[x,y], …]` — polygon of the net interior in image coordinates (where pucks count as IN). |
| `approach_roi` | `null` | `[[x,y], …]` — polygon of the approach / shooting zone in front of the goal line. Drawn manually in step 4 of `--calibrate`. Falls back to auto-mirroring `net_roi` across the goal line if absent. |

### Detection method

| Key | Default | Description |
|---|---|---|
| `detection_method` | `"motion"` | How to find puck candidates per frame. |

Valid values:

- `"motion"` — MOG2 background subtraction. Detects anything that's *changed* from the learned background. Sensitive to shadows, lighting changes, and the goalie moving.
- `"dark"` — brightness threshold only. Detects anything *darker* than `dark_threshold`. Best for a black puck against a brighter background. Doesn't care about motion, so will pick up static dark things in the ROI (problematic if the net interior itself is dark).
- `"combined"` — pixel must be both moving (MOG2) AND dark (brightness). Best for a black puck on a bright background where shadows or lighting drift are causing false positives. Slightly more CPU than either alone.

### Detection tuning (motion / MOG2 path)

| Key | Default | Description |
|---|---|---|
| `bg_history` | `300` | How many recent frames MOG2 averages over to build its background model. Higher = more stable model, slower to adapt to lighting changes. |
| `bg_var_threshold` | `30` | MOG2 sensitivity. Lower = more pixels classified as foreground (more sensitive). Raise to 50-80 if you see noise/shadows passing through. |
| `detect_shadows` | `true` | Use MOG2's built-in shadow classifier. Marks shadow pixels with value 127 in the foreground mask, so they can be filtered out by `fg_threshold`. |
| `fg_threshold` | `200` | Pixels in the foreground mask above this value count as real foreground. With `detect_shadows: true`, set above 127 to exclude shadows. Range: 128 (anything passes including shadows) to 254 (only the most confident foreground). |

### Detection tuning (dark threshold path)

| Key | Default | Description |
|---|---|---|
| `dark_threshold` | `60` | Pixel-brightness cutoff for `"dark"` and `"combined"` methods. Pixels darker than this become candidate puck pixels. Lower = stricter (puck must be very black). Tune by watching the foreground mask in `--debug`. |

### Contour filtering

| Key | Default | Description |
|---|---|---|
| `puck_min_area` | `80` | Minimum contour area in **full-resolution pixels** to be considered a puck. Tune with `verbose_contour_logging` to find what your real puck areas are. |
| `puck_max_area` | `4000` | Maximum area. Bump up if motion-blur streaks elongate the puck blob. Note: a puck close to a top-down camera can be 5-10x larger than one at the back of the net (perspective). |

### Image processing

| Key | Default | Description |
|---|---|---|
| `process_scale` | `0.5` | Downscale factor for the CV pipeline. `0.5` runs CV on 640×360 from a 1280×720 capture — 4x faster, plenty of detail for puck detection. The displayed image and calibration coordinates remain at full resolution. |
| `morph_close_size` | `13` | Kernel size for the morphological close op (odd integer). The close op merges nearby fragments of fast-moving objects into one blob — critical for high-speed pucks where MOG2 outputs a cloud of small fragments instead of one solid shape. **Sized for the processed image** — at scale 0.5, a 13px kernel covers what a 26px kernel would at full res. |
| `morph_open_size` | `3` | Kernel size for the morphological open op. Removes single-pixel speckle noise. Keep small. |

### Tracking

| Key | Default | Description |
|---|---|---|
| `min_track_hits` | `2` | A track must be matched in this many frames before it's eligible to score a goal. Filters out single-frame flickers. Higher = stricter (more reliable, slower to react). |
| `tracker_max_dist_px` | `250` | Max pixel distance between consecutive frames for a detection to be matched to an existing track. Should be large enough that a fast puck doesn't outrun the matcher. At 120fps a 30 m/s puck moves ~30-100px between frames depending on camera mount. |
| `tracker_max_age_s` | `0.4` | A track is dropped if no detection matches it for this long. |

### Goal logic

| Key | Default | Description |
|---|---|---|
| `armed_window_seconds` | `1.0` | After receiving `shot_incoming`, look for goals for this long. Emits `no_goal` if nothing scored before window expires. |
| `goal_cooldown_seconds` | `0.5` | Minimum gap between consecutive goal events. Belt-and-suspenders against double-counting. |
| `always_on_default` | `false` | Mode at startup. `false` = armed (waits for `shot_incoming`); `true` = always-on (continuous detection). Can be flipped at runtime via WebSocket. |
| `log_level` | `"INFO"` | Standard Python log levels: `"DEBUG"`, `"INFO"`, `"WARNING"`, `"ERROR"`. |

### Debug display

| Key | Default | Description |
|---|---|---|
| `debug_display_scale` | `0.5` | Scale of the `--debug` imshow windows. `0.5` cuts GUI work to ~25%, helpful on Pi where imshow is the dominant cost in debug mode. The detection pipeline is unaffected — only the displayed copy is resized. |
| `debug_goal_flash_seconds` | `0.5` | How long the green GOAL banner stays on the debug overlay after a goal is detected. |

### Verbose diagnostic logging

For tracking down false negatives ("why didn't that puck get detected?").
Disabled by default — turn on temporarily, throw test pucks, then turn off.

| Key | Default | Description |
|---|---|---|
| `verbose_contour_logging` | `false` | If true, log every accepted contour and every contour that *almost* passed (within `verbose_contour_log_margin` of the area thresholds). Output goes to the same console as the timing info. |
| `verbose_contour_log_margin` | `0.5` | Fractional tolerance for "interesting" rejected contours. `0.5` logs anything 50%-200% of the area bounds. With `puck_min_area: 3000, puck_max_area: 4000` and margin `0.5`, the script logs anything 1500-6000 px. |
| `verbose_log_throttle_hz` | `5` | Maximum log lines per second across all contours, to avoid drowning the console on a noisy frame. |

Each verbose line shows: verdict (ACCEPT/REJECT), area in full-res pixels,
position, bbox dimensions, aspect ratio, and the rejection reason.

Example output:

```
13:22:14 [INFO] contour ACCEPT area=3450 pos=(642,310) bbox=64x58 aspect=1.10
13:22:14 [INFO] contour REJECT area=2850 pos=(640,308) bbox=58x52 aspect=1.12 (below min=3000)
13:22:15 [INFO] contour REJECT area=8200 pos=(450,520) bbox=140x60 aspect=2.33 (above max=4000)
```

The third line in that example is interesting: aspect 2.33 means it's quite
elongated — probably motion-blurred puck or a goalie body part, not a clean
puck shape. That kind of pattern is what you're looking for.

## Tuning guide for false negatives

Symptoms: real pucks aren't being detected as goals.

1. **Run with `verbose_contour_logging: true`.** Throw the puck. Look at the
   log. Did the contour show up at all? If yes, why was it rejected?

2. **Common patterns and fixes:**
   - "REJECT (below min)" with area only 10-30% below `puck_min_area`:
     lower the min.
   - "REJECT (above max)" with area only 10-30% above `puck_max_area`:
     raise the max.
   - No contour logged at all near the puck position: detection is failing
     upstream (MOG2 / dark threshold is missing the puck). Try
     `--debug` to see the foreground mask.
   - Contour ACCEPT but no goal event: track never accumulated enough hits
     (`min_track_hits`), or the cross direction was wrong, or the track's
     first position was already past the line (approach zone too small —
     re-check calibration).

3. **Per-position area variation:** a top-down camera sees a puck closer to
   the lens as much larger than one farther away (perspective). Widen
   `puck_min_area` / `puck_max_area` to span the full range you observe.

---

## Tuning guide for false positives

Symptoms: goals are being detected when they shouldn't be.

1. **Tighten `puck_min_area` / `puck_max_area`** based on real puck readings.
2. **Raise `bg_var_threshold`** to make MOG2 less sensitive.
3. **Switch `detection_method` to `"combined"`** if the false positives are
   shadows (combined mode requires the pixel to be both moving AND dark).
4. **Raise `min_track_hits`** to require more frames of confirmation. Watch
   for the trade-off — stricter filtering can cause false negatives.

## Wire format (WebSocket)

All messages are JSON. The detector connects out as a client.

### Outbound (detector → server)

```json
{ "type": "hello", "net_id": "net_1", "ts": 1730000000.123 }

{ "type": "heartbeat", "net_id": "net_1", "ts": 0,
  "fps": 119.2, "mode": "armed", "armed": false, "tracks": 0 }

{ "type": "goal", "net_id": "net_1", "ts": 0,
  "track_id": 17, "speed_px_s": 1240.5,
  "shot_id": "shot_1730000000123", "mode": "armed" }

{ "type": "no_goal", "net_id": "net_1", "ts": 0,
  "shot_id": "shot_1730000000123", "reason": "window_expired" }
```

### Inbound (server → detector)

```json
{ "type": "shot_incoming", "shot_id": "shot_1730000000123" }
{ "type": "set_mode", "mode": "always_on" }
```

`shot_id` is opaque — the detector echoes whatever the server sent back in
the goal/no_goal response so events can be correlated.

When the real Node app is ready:

2. The Node app should accept WebSocket connections, recognize `hello` to

   during install but the production system doesn't need them.

## Lucid Vision GigE camera (PHX004S)

Set `capture_backend: "lucid"` in `config.json`. The `source` key is ignored —
the camera is discovered automatically via `arena_api`.

### One-time setup

1. **Install Arena SDK** — download from Lucid's downloads hub (Windows or Linux installer)
2. **Install Python wrapper** — `pip install arena_api`
3. **Assign camera IP** — use `IpConfigUtility` (bundled with Arena SDK) to give
   the camera a static IP on the same subnet as your GigE NIC
4. **Enable jumbo frames** — set MTU 9000 on the GigE NIC (Device Manager →
   adapter properties → Advanced → Jumbo Packet). Required for sustained throughput.
5. **Update resolution** — the PHX004S native resolution is ~720×540. Set
   `frame_width: 720` and `frame_height: 540` in `config.json` (requesting an
   unsupported size will error at startup).

### Exposure for Lucid

Use `lucid_exposure_us` (microseconds) when `auto_exposure: false`. The standard
`manual_exposure` key is an OpenCV log2-seconds value and is ignored for the Lucid
backend. 7800 µs ≈ 1/128 s.

### How it works

The `LucidCapture` class wraps `arena_api` with the same `.read()` / `.release()`
interface as `cv2.VideoCapture`. The PHX004S streams Mono8 frames; `LucidCapture`
converts each frame to BGR before returning it so the CV pipeline is unchanged.

## Hardware path on the Pi

Currently uses USB capture via OpenCV's V4L2 backend. For the **CSI OV9281**
the right approach is `picamera2` with raw mono frames — lower latency,
lower CPU, no USB negotiation. To swap it in, replace the `open_capture`
function and the `cap.read()` loop body; everything downstream is
camera-agnostic.

Sketch:

```python
from picamera2 import Picamera2
picam = Picamera2()
picam.configure(picam.create_video_configuration(
    main={"size": (1280, 800), "format": "YUV420"},
    controls={"FrameRate": 120}))
picam.start()
# in loop:
yuv = picam.capture_array("main")
gray = yuv[:800, :]   # Y plane only
```

## Known issues and gotchas

- **Windows MEP cap:** Windows 11 24H2+ has a "Modern Effects Pipeline" that
  silently caps USB cameras at 60fps. Disable per-camera in
  Settings → Bluetooth & devices → Cameras → "Basic camera mode".
- **Linux GStreamer fallback:** the `auto` capture backend should pick V4L2
  on Linux. If it falls through to GStreamer, set `capture_backend: "v4l2"`
  explicitly.
- **Pi 5 thermal:** sustained CV at 120fps on one core warms the SoC. Use
  the active cooler. Check `vcgencmd measure_temp` and `vcgencmd get_throttled`
  if performance drops over time.
- **Externally managed environment** (Debian/RPi OS): `pip3 install` may
  refuse to install into the system Python. Use `--break-system-packages`
  or set up a venv with `--system-site-packages`.
